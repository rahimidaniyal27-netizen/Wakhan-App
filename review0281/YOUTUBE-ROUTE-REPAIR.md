# Guarded YouTube route/readiness repair

Observed operator result after browser recovery: token health HTTP200, browser running, no error; metadata succeeds in 4.25s, muxed format, signed URL IPv6, no configured proxy. Both aiohttp and yt-dlp CDN requests receive HTTP403. This confirms a media-access failure after extraction, not the previous dead-browser failure. It does not prove that IPv6 is its cause.

The reviewed resolver previously discarded yt-dlp's `available_at` timestamp. yt-dlp derives it from source-advertised pre-playback timing; immediate requests can be refused even with valid metadata. The relay also did not preserve the signed URL's IP family. This patch waits for the advertised timestamp (maximum20s) before returning YouTube metadata and keeps direct YouTube CDN requests on the URL's family, including salon audio. YouTube worker/request limits are32/34s so a bounded source-readiness wait fits; SoundCloud retains its12/14s limits and automatic IP family. Configured HTTP/SOCKS proxy routing, CDN allowlists, TLS validation, authorization, resource/range limits and private cookie copies remain in use.

`repair-youtube-route.py --apply` checks the exact original application cohort and the installed private runtime. It leaves the recovered browser alone. In temporary source copies, it first tests the readiness/family correction with the existing source configuration. If actual CDN bytes and FFmpeg audio decoding do not succeed, it tests a newly extracted URL using IPv4 for YouTube extraction and transfer. Only a successful mode is installed. IPv4 selection is scoped to YouTube's existing configure hook and does not disable IPv6 on the machine or change VPN/SSH/firewall/service policy.

A successful trial permits a single nine-file application transaction: the six pending playback/salon-photo files, shared playback transport, private runtime configuration and movie-worker import. The updater backs up only reviewed source files, restarts only wakhan-app, verifies app health/auth/sign-in configuration and the real leased personal-music route with FFmpeg and signal detection. Failure restores all nine source files while retaining user messages and browser recovery. A private source-only rollback command is printed. If neither trial works, the app is left unchanged, a nonzero exit status is returned, and a safe JSON result is printed as well as saved in a private ZIP.

Validation:19 focused tests on Python3.12 covering exact-family connectors, default SoundCloud/proxy behavior, pool limits, actual HTTP Range headers, bounded readiness, caller-supplied worker deadlines, both trial choices, blocked-CDN gating, actual subprocess/MP4/FFmpeg checks, nine-file automatic and offline rollback, and preservation of new user messages. Eight command tests also pass on Python3.13. Nineteen existing selector, real salon-route/FFmpeg and isolated-worker tests passed against the new payloads. No production CDN or phone test has been performed from this workspace; success on the operator's server is a deployment prerequisite, not a claimed result. No native client build is included.
